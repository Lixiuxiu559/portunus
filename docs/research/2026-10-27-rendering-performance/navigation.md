# 刷新后的首次菜单切换验证

同日用户反馈 Cmd+R 后每个菜单首次进入均有等待。基线使用[装饰动画优化](README.md)后的 Dev 产物。真实点击六个菜单并通过 DOM 观察记录，其他五页首次提交内容均在点击后约 308–314ms，API 直到页面挂载后才开始，通常只耗时 1–4ms；重复进入则不再有固定等待。这支持主要瓶颈在首次懒加载触发的 Suspense 阶段，而不是后端查询。

调整为首屏继续按需加载，挂载后利用空闲回调逐页预加载其余页面模块；悬停或键盘聚焦菜单时优先准备目标页。预加载完成的页面在挂载时直接使用组件，避免已缓存的 import Promise 再触发一次 Suspense。挂载后固定组件身份，后台加载完成不会把正在编辑的页面替换重挂载。未预加载完成时仍保留原有懒加载和失败提示。

预加载仅加载界面代码，不挂载页面，不发起各页业务请求，不保存数据到浏览器存储。任务执行一轮后结束，卸载取消后续任务；加载失败允许下次重新尝试。代价是在首屏显示后提前解析其余菜单代码、占用对应模块内存；未增加常驻轮询。

同一 1280×720 可见 Dev 窗口，Cmd+R 后首屏等待 1.5 秒，依次真实点击各菜单。下表是内容进入就绪状态后再等待两个 requestAnimationFrame 的时间，不包含已有 180ms 入场动画播放完毕的等待，也不是屏幕像素级延迟测量。

| 首次切换 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 模型 | 336.5ms | 35.1ms |
| 分组 | 325.6ms | 51.5ms |
| 日志 | 358.4ms | 70.6ms |
| 接入 | 338.3ms | 33.3ms |
| 设置 | 316.0ms | 19.5ms |

优化后另一轮完整刷新中，只观测到当前渠道页的 `/api/channels` 和 `/api/quota/summaries` 请求，没有提前请求其他页业务接口。随后的 20 秒静置测得 GPU Helper CPU 0.10%、Renderer 0.02%、主进程 0.04%，保持低负载。

`pnpm test` 205/205、类型检查、Dev 打包、差异空白检查通过。新增验证覆盖预加载与前台加载去重、同步读取已完成模块、失败重试、逐页调度、取消及加载途中卸载。另以 Dev 实测覆盖刷新后首次进入和再次进入所有菜单。未调整导航守卫或缓存新鲜度规则；本轮未进行独立三轴、复杂度或突变审计。

原始样本及条件见 [navigation-measurements.json](navigation-measurements.json)。短时样本不能保证任意设备、极早点击或大数据量下都达到同样延迟；预加载尚未完成时仍可能出现加载占位。
