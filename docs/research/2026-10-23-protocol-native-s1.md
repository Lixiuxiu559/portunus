> 后续决策：strict/legacy 转换策略配置及请求侧拒绝分支已移除。本文涉及策略开关的内容是阶段历史；当前统一保留诊断、沿用正常调用行为，安全边界始终执行，见[当前诊断模式](2026-10-23-protocol-diagnostics-only.md)。

## 需求与范围

用户批准先实施原生扩展保留和目标兼容检查，保持现有调用行为，strict 不默认开启。此阶段是请求侧基础设施，响应侧扩展、类型化流式、预提交缓存及全局重试预算仍按后续阶段处理。

strict 表示显式阻止已识别的不可表达能力和无法验证的原生续接状态。当前检查覆盖有限协议构造，不是所有嵌套字段的无损证明，也不验证供应商模型实际支持能力。

## 配置

默认是 `legacy`，旧配置文件和零值协议选项保持兼容。

```json
{"proxy":{"conversion_policy":"legacy"}}
```

环境变量 `PORTUNUS_PROXY_CONVERSION_POLICY` 覆盖配置，允许 `legacy` 或 `strict`；非法值启动时报错，空配置视为 legacy。修改配置后在下一次启动生效，未新增 UI 开关。本轮不改用户现有配置、不重启应用。

- legacy：记录已识别问题，仍按已有转换、搜索映射和工具剥离规则执行；来源无法验证的签名/密文继续按旧规则处理。
- strict：本目标已识别为不可表达时，发送前跳过并查找其他分组成员；所有成员不支持则返回 400。不可验证的原生状态引用/签名属于请求级失败，停止整个候选链。尚未实现可信跨请求绑定，所以不适合直接对全部原生多轮调用开启。

## 代码与数据边界

- `CaptureRequest` 保存请求原始快照和 request/tool/item/block 片段、原始位置；`Native()`/`Original()` 返回深拷贝。
- `PrepareTarget` 为本次目标准备独立请求，兼容检查结果随 ComposeStats 返回；生产网关沿原 ComposeUpstreamRequest 入口接入。
- 同协议的必要字段覆盖改为 RawMessage，避免无关大整数经过 float64。零覆盖保留原 body；不承诺覆盖后的对象键顺序/空白不变。
- 跨协议继续使用既有 canonical 映射。保留原始片段不等于把它们复制到其他协议；此阶段不做未经规则允许的原生恢复。
- 来源统一标记 unverified，不因客户端提交 source 元数据而升级可信度。
- 原生正文/片段不参与默认 JSON 序列化，也不写日志。日志只新增策略、检查范围 `request_native_v1`、是否检查、是否发现已检查范围内的问题、问题类别数摘要。
- 旧日志 `conversion_checked=false` 表示未采集；`conversion_compatible=false` 不能单独解释为转换失败。Compatible=true 也只表示本阶段已检查规则未发现问题。
- 兼容性跳过不会产生 HTTP attempt，也不计模型熔断失败。旧 relay 日志仍可记录一次准备失败，不能把其行数当作 Do 次数。
