## 2. 推荐产品定位与受众

对外一句话：**给 Claude Code / Codex 用户的桌面模型管家：集中管理 API 渠道，配置备用模型，看清每次调用成本。**

用户利益表达顺序：少改配置 → 管理备用渠道 → 看清成本 → 在需要时解释协议转换。

优先受众：已经在用 Claude Code 或 Codex、自己持有 API Key、同时使用或准备使用两个以上渠道的个人开发者。

其次：已有 API 编程使用经验，想把渠道和调用记录集中管理的独立开发者。等首批内容有证据后，再探索技术型 AI 工具作者。

首阶段少做面向泛 AI 用户的“工具合集”“AI 赚钱”“零基础装完就能用所有模型”。这些主题容易吸引没有 API Key 或实际使用需求的人。

差异表达：突出“桌面安装、个人使用、客户端配置与路由及日志集中管理”；不宣称全面胜过服务端网关或其他配置切换工具。

## 3. 账号定位

建议两平台使用统一的开发者身份，保持名称和头像一致。默认以作者本人配音、屏幕录制为主，可以不出镜。

- 名称：`[你的昵称]｜AI 编程工具实测`。
- 简介：`Portunus 作者｜分享 Claude Code / Codex 配置、多渠道管理与调用成本实测。产品演示与安装说明见置顶。`
- 头像：优先稳定的本人或个人形象，封面角落固定放 Portunus 标识。若已有成熟个人账号，沿用身份。
- 身份：透明说明产品由自己开发，区分作者演示与第三方体验。
- 内容比例起点：60% 痛点与教程，25% 可复现的功能实验，15% 开发过程和需求反馈；比例仅用于安排选题，不当作平台规律。
- 置顶三篇：适合谁与完整演示；首次接入教程；API Key、费用、备份、兼容边界 FAQ。

抖音分工：用一个看得懂的操作结果引出问题。先试 30–60 秒的录屏配音，单条只讲一个价值。

小红书分工：做用户能搜索和收藏的步骤说明。先试 5–7 页图文，包含前置条件、关键步骤、结果和边界；复杂操作保留录屏版。

两边素材可共用，但标题、首屏和说明要重做。产品名用于建立记忆，用户问题用于帮助理解和搜索。

## 5. 前三条制作稿

### 第一条：配置麻烦 → 集中管理

抖音建议 40–50 秒，时长只是剪辑起点。

- 0–4 秒：放大配置画面。配音：“用 Claude Code 换 API 渠道，你也要重新改地址、Key 和模型名吗？”
- 4–10 秒：展示产品。配音：“我做了 Portunus，把渠道和模型分组集中在一个桌面应用里。”
- 10–27 秒：添加脱敏渠道、选择已有模型、加入分组，展示客户端指向分组。
- 27–38 秒：在分组里切换所用上游，再发一条测试请求，在日志里核对；客户端入口保持不变。
- 38–48 秒：配音：“它需要你自备 API Key。完整接入过程放在置顶，你现在用几个渠道？”

小红书改编：第 1 页“换渠道怎么少改配置”；第 2 页说明适合的人；第 3 页渠道管理；第 4 页分组；第 5 页客户端配置；第 6 页调用结果与限制。每页一个操作，截图局部放大。

### 第二条：第一次接入

抖音展示全流程关键节点，不能把剪辑后时长写成真实安装耗时。小红书按“前提 → 安装包选择 → 添加渠道 → 建分组 → 保存客户端配置并重启 → 检查日志”制作。Codex 与 Claude Code 教程分开，以免步骤混淆。

讲清：Key 来源由用户选择；先确认已有渠道可用；出现安装提示时看官方项目安装说明；配置保存按钮按当前 UI 实际操作讲解，不宣传成无需确认的一键万能接入。

### 第三条：是否适合你

三个适用情况：有多个 API 渠道；经常调整 Claude Code / Codex 接入配置；需要对照调用日志看用量。说明产品不提供模型和额度，不能扩展模型上下文或保证上游永久可用。最后展示三步上手路径。

## 6. 发布和反馈承接

单人每周用一个集中录制时段拍两组素材，分别剪辑抖音版和小红书版。先准备三条，再开始发，避免边做账号边临时找选题。

站内内容 → 主页置顶教程 / FAQ → 在账号实际具备且平台允许的入口提供安装说明 → 下载 → 首次调用成功 → 第 7 天自愿回访。入口能力要实际确认；不默认外链可点击，不靠暗号或绕过限制完成引流。

安装说明需要让用户容易找到：产品用途、适用系统、自备 Key、下载来源、完整步骤、安装提示解释、费用估算口径、问题反馈方式。当前统一参考 GitHub Releases latest；未验证国内首次下载体验，不直接承诺下载顺畅。

常用回复：

- “我是这个工具的作者。它负责管理你已有的 API 渠道，不提供模型额度。”
- “费用按你配置的模型价格和上游返回的用量估算，最终账单看上游。”
- “你是在安装、添加渠道，还是保存客户端配置时卡住？发报错文字即可，不要发 API Key。”

## 7. 四周验证与衡量

- 第 1 周：前两组，观察用户能否理解产品、能否照教程接入。
- 第 2 周：适合谁、备用渠道两组，归纳真实需求；修订置顶 FAQ。
- 第 3 周：费用与 Codex 两组，对最有效主题更换一个标题或开头继续测。
- 第 4 周：备份与作者故事两组，回访愿意反馈的试用者。

每篇记录平台、题目、发布时间、制作时长、曝光/播放、收藏、主页访问（可获得时）、有效咨询、可归因的首次调用成功人数。首次成功采用用户自愿反馈或已有数据，不假设桌面应用已具备来源归因和留存统计。

“有效咨询”指已经使用相关客户端或持有 Key，询问兼容、接入、备用渠道或费用的人；只问是否送额度的人单独记录。“首次成功”指通过 Portunus 完成一次请求；“第 7 天仍在用”与“当天已下载”分开统计。

首月先尝试找到 10 位能完整反馈的目标用户，这是行动目标，不是增长预测。样本小时逐条复盘，不使用虚假的行业转化率标准。

判断原则：

- 看的人多但目标咨询少：标题受众太泛，改回具体客户端和问题。
- 收藏多但无法完成接入：补教程、安装说明，优先改善卡点。
- 试用多但一周后不再用：调查使用频率、替代工具、稳定性和重复价值。
- 曝光少但有人完整接入：继续验证相同人群与主题，不凭一条数据下结论。

## 9. 对外口径与待确认项

保留的真实卖点：桌面安装、多渠道集中管理、配置备份回滚、按优先级配置备用模型、日志与费用估算。

避免承诺：所有模型与工具完全兼容、任意流中断无缝续接、必定省钱、免费无限模型、配置标记扩大真实上下文、数据永不离开本机。模型请求仍会发送到用户选择的上游。按现有宣传约定，未确认授权许可证前不称“开源”。
