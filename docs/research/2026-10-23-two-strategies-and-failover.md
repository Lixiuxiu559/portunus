# 仅保留手动与故障转移，以及后续可靠性改进

> 当前状态：本文记录策略收敛时的历史分析；其中429作用域冷却、半开有限探测、切换诊断和可选渠道并发上限均已完成。下文“尚未实施/后续建议”不是当前待办。现在停止扩展，见[实际验收](2026-10-23-protocol-failover-acceptance/README.md)与[集中待办](2026-10-23-protocol-failover-backlog.md)。

## 本次实施范围

用户决策：保留现有模式，只留下手动和故障转移；移除轮询，分析故障转移可以借鉴 AxonHub 的机制。本轮实施策略收敛，不引入加权、评分、自适应或会话亲和，也不修改现有 gateway 的重试和熔断语义。

- `manual`：只调用激活成员。未激活仍提示配置不完整，失败可以按现有规则重试同一成员，不自动换成员。
- `failover`：固定主备顺序，优先调用靠前且未被熔断挡住的目标；符合切换条件才顺延。每次新请求仍从主目标开始。
- 创建/更新接口及前端表单只接受上述两种策略，新的 `round_robin` 请求返回 400。
- 历史数据库中精确的 `round_robin` 值在应用启动、表结构迁移完成后转为 `failover`。保留分组、成员、优先级、激活项和其他字段；迁移可重复执行，失败则不启动服务。未启动正式服务，也未直接修改正式数据库。
- 成员按 `priority` 升序，同优先级按成员 ID 升序，确保历史轮询数据转换为固定且可调整的主备顺序。前端继续支持故障转移拖拽排序，默认创建策略仍为手动。

## 当前故障转移已具备的能力

`router.Resolve` 构造固定顺序，`gateway` 负责逐目标执行与失败动作。当前默认每目标最多3次尝试，但整个请求总计最多4次显式 HTTP Do，兼容重试也占用预算。流式首内容期限和非流式累计期限跨目标共用，后续发送统一可取消退避。等响应头假死会直接换目标；模型级熔断状态跨分组共享。

已经交付流内容、原生操作不允许重放、客户端取消、本地资源超限、请求预算或累计期限耗尽都会阻止不安全的后续发送。不应为了“更容易切换”放宽这些边界。兼容诊断仍只做诊断，不恢复 strict。

## 可借鉴的机制：不改变固定主备顺序

对照本次会话读取的 AxonHub `unstable` 提交 `03437bb137793fc930084b356454233118a8ea92`。以下是后续设计建议，尚未实施。

### 1. 429不重复打同一目标，并记录有作用域的冷却（优先）

当前 Portunus 将上游429视为可重试错误，与5xx一起计入模型熔断，可能在同一模型上先消耗多次尝试。最终错误的 Retry-After 可透传给客户端，但尚未形成跨请求的内部限流冷却。

AxonHub 的 `CanRetry` 对429明确返回false以跳过同渠道重试，随后尝试后续候选。它也记录冷却状态，但评分中的负分不等于硬排除，不能直接照搬为本产品的可用性约束。[上游重试源码](https://github.com/looplj/axonhub/blob/03437bb137793fc930084b356454233118a8ea92/internal/server/orchestrator/outbound.go#L1033)、[冷却评分源码](https://github.com/looplj/axonhub/blob/03437bb137793fc930084b356454233118a8ea92/internal/server/orchestrator/lb_strategy_rate_limit.go#L92)。

建议：对允许重放的调用，429后停止当前目标重试，按既有主备顺序寻找未冷却的下一项；合法 Retry-After 支持秒数和HTTP日期，裁剪到可配置上限，缺失/非法值用有界默认冷却。冷却只影响候选是否暂时可用，不动态改变优先级；手动模式不自动换成员。冷却中的跳过不造HTTP attempt，也不扣Do预算，真正切换仍受总预算、deadline与退避控制。

429可能是模型限额，也可能是账户/渠道限额。不能仅凭状态码将整个渠道所有模型一起屏蔽：默认采用已确认的最小作用域，只有明确的上游信号或渠道配置才扩展为渠道级。限流冷却和真实故障熔断分开记录；配置/凭据变更需失效关联状态。

### 2. 半开恢复用有限探测名额（优先）

当前 `BreakerStore.Allow` 对半开直接放行，冷却结束后多个请求可能同时返回主目标；注释里的“一个探测”尚无并发名额保证。AxonHub 用 `TryBeginProbe/EndProbe` 原子占用与释放探测资格。[探测源码](https://github.com/looplj/axonhub/blob/03437bb137793fc930084b356454233118a8ea92/internal/server/biz/model_circuit_breaker.go#L337)。

建议：以真实用户请求触发有限探测，不新增后台生成调用；同一模型的其他请求继续按主备顺序使用备用。成功逐步恢复，失败重新冷却；取消、本地限制与装配失败释放名额但不误算为供应商失败或恢复成功。租约带代次，避免旧请求的迟到结果改变新一轮熔断状态。主目标恢复后，新请求重新优先使用主目标，不做会话粘性。

### 3. 失败动作和切换原因更可解释

沿用现有 `failSpec` 单一裁决，进一步明确哪些错误应“同目标重试”“跳过目标”“停止整个请求”，不在路由器或协议层复制一套规则。429、目标限额、鉴权配置故障和瞬时网络错误应有各自处理；不能把所有400都当成客户端不可恢复错误，也不能把所有403都当成渠道永久失效。

观测可补充：为什么跳过主目标、冷却剩余多久、是否占到恢复探测名额、为什么选择备用、为什么整个请求停止。继续区分候选跳过/relay行和实际Do，不为预检查或等待制造HTTP attempt，不把旧日志统计宣称为完整请求终态。

### 4. 可选渠道并发上限（后续）

固定主备模式仍可能让主渠道积累太多长请求。可借鉴 AxonHub 的原子并发准入，把“渠道满载”作为暂时不可用条件，然后顺序尝试备用；无需引入负载分数。应使用有界队列或明确拒绝，并在取消、失败、正常结束时释放名额，不能无界等待。当前单请求的body/全文限额不等于渠道并发容量。
