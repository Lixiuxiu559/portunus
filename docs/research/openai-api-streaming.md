# OpenAI Chat Completions 与 Responses API 官方规范研究笔记

> 研究时间：2026-08-27。对象：OpenAI 官方 API 规范（`openai/openai-openapi` 仓库的 `openapi.yaml`，version 2.3.0）。
> 目的：为 `backend/protocol/` 的 OpenAI↔Anthropic↔Gemini 协议转换层提供权威字段规范，重点是流式 chunk 结构、usage / reasoning / 多模态字段的「官方标准 vs 第三方扩展」边界，以及转 Anthropic 时容易断链的字段。

---

## 1. 一句话结论

OpenAI **官方规范里没有 `reasoning_content` 字段**——它是 DeepSeek 等兼容方的扩展；官方表达「思考/推理」用的是请求参数 `reasoning_effort` + usage 里的 `completion_tokens_details.reasoning_tokens`，而「思考内容本身」只在 Responses API 里以 `reasoning` item（`reasoning_text`/`summary_text`/`encrypted_content`）形式存在，Chat Completions 官方流式里**不流式吐思考内容**。流式 chunk 的 `id`/`created`/`model`/`object`/`system_fingerprint` **每个 chunk 都重复携带**（不是只在第一个），`delta.role` 只在首个 chunk，`delta.tool_calls[].function.arguments` 是**需要按 index 拼接的 JSON 分片**；usage 默认只有非流式返回，流式要 `stream_options.include_usage=true` 才会在末尾额外多一个 chunk。转换层最要命的三处断链：①OpenAI 用 `data: [DONE]` 收尾 vs Anthropic 用 `message_stop` 事件；②`finish_reason` vs `stop_reason` 枚举映射；③两者的 usage 语义**相反**（OpenAI `prompt_tokens` 含缓存命中，Anthropic `input_tokens` 不含缓存、缓存另计）。

主要来源：
- https://platform.openai.com/docs/api-reference/chat/create （请求参数）
- https://platform.openai.com/docs/api-reference/chat/streaming （流式说明）
- https://platform.openai.com/docs/api-reference/responses/create （Responses API）
- `openai/openai-openapi` 仓库 `openapi.yaml`（字段的唯一权威枚举来源，本文所有「必有字段 / 枚举值」均据此，URL 见各小节）

## 2. Chat Completions 流式 chunk 结构（`ChatCompletionChunk`）

来源：openapi.yaml `CreateChatCompletionStreamResponse` schema + x-oaiMeta 官方示例。文档页：https://platform.openai.com/docs/api-reference/chat/object

| 字段 | 类型 | 必填/可选 | 说明 |
|---|---|---|---|
| `id` | string | **必填** | 本次 chat completion 的唯一 ID。**每个 chunk 携带同一个 ID**（官方："Each chunk has the same ID"） |
| `object` | string | **必填** | 恒为 `"chat.completion.chunk"` |
| `created` | integer(unixtime) | **必填** | 创建时间戳。**每个 chunk 相同**（"Each chunk has the same timestamp"） |
| `model` | string | **必填** | 模型名。**每个 chunk 都重复携带** |
| `choices` | array | **必填** | 候选数组。`n>1` 时多个；`include_usage=true` 时**最后一个 chunk 可以是空数组** |
| `usage` | CompletionUsage | 可选 | 仅当设置 `stream_options: {include_usage: true}` 时出现；**除最后那个 chunk 外，其余 chunk 的 usage 为 null** |
| `system_fingerprint` | string | 可选(已废弃) | 后端配置指纹（用 seed 判断确定性时参考） |
| `service_tier` | string | 可选 | 服务层级 |
| `obfuscation` | string | 可选 | 防侧信道的随机填充串，默认携带；`stream_options.include_obfuscation:false` 时省略 |
| `moderation` | object/null | 可选 | 请求了 moderated completions 时的审核结果 |

**关键结论：id / created / model / object 在每一个 chunk 里都重复出现**，不是只在第一个 chunk 带。官方示例（openapi.yaml `x-oaiMeta.example`）三段 chunk 全部携带相同 `id/model/created/system_fingerprint`：

```json
{"id":"chatcmpl-123","object":"chat.completion.chunk","created":1694268190,"model":"gpt-4o-mini","system_fingerprint":"fp_44709d6fcb","choices":[{"index":0,"delta":{"role":"assistant","content":""},"logprobs":null,"finish_reason":null}]}
{"id":"chatcmpl-123","object":"chat.completion.chunk","created":1694268190,"model":"gpt-4o-mini","system_fingerprint":"fp_44709d6fcb","choices":[{"index":0,"delta":{"content":"Hello"},"logprobs":null,"finish_reason":null}]}
{"id":"chatcmpl-123","object":"chat.completion.chunk","created":1694268190,"model":"gpt-4o-mini","system_fingerprint":"fp_44709d6fcb","choices":[{"index":0,"delta":{},"logprobs":null,"finish_reason":"stop"}]}
```

### 2.1 `choices[]` 元素（chunk 内）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `index` | integer | 必填 | 候选序号 |
| `delta` | object | 必填 | 增量内容（见下） |
| `finish_reason` | string/null | 必填 | 停止原因。**只在最后一个（或每个候选最后一个）chunk 出现**，其它 chunk 为 null |
| `logprobs` | object/null | 可选 | 请求了 `logprobs` 时的对数概率 |

### 2.2 `choices[].delta` 结构（`ChatCompletionStreamResponseDelta`）

| 字段 | 类型 | 必填/可选 | 说明 |
|---|---|---|---|
| `role` | string | 可选 | **只在第一个 chunk** 出现，取值 `assistant`（枚举还有 `developer/system/user/tool`）。之后 chunk 的 delta 不再带 role |
| `content` | string **或 null** | 可选 | 文本增量。**每个 chunk 一段字符串片段，需拼接**；也可能是 null（如纯 tool 调用、最终 chunk） |
| `tool_calls` | array | 可选 | 工具调用增量（见 2.3） |
| `function_call` | object | 已废弃 | 旧版单函数调用，被 `tool_calls` 取代（`deprecated: true`） |
| `refusal` | string / null | 可选 | 模型拒答内容 |

### 2.3 `delta.tool_calls[]`（`ChatCompletionMessageToolCallChunk`）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `index` | integer | 必填 | **用于关联多个并行工具调用**：同一次生成里的多个 tool call 各占一个 index，arguments 分片按 index 归并 |
| `id` | string | 可选 | 该 tool call 的 ID，**在首次出现的 chunk 带** |
| `type` | string | 可选 | 恒为 `function` |
| `function.name` | string | 可选 | 函数名，**在首次 chunk 带** |
| `function.arguments` | string | 可选 | **JSON 分片字符串**。每个 chunk 一段，需跨 chunk **拼接**后才能得到完整 JSON。官方原话："The arguments to call the function with, as generated by the model in JSON format. Note that the model does not always generate valid JSON" |

**关键结论：`delta.content` 和 `delta.tool_calls[].function.arguments` 都是「每个 chunk 一段、需拼接」的分片**，arguments 尤其不是完整 JSON；`index` 字段是区分并行多个 tool call 的关键（深见官方流式 tool 调用示例中 `{"index":0,"type":"function","function":{"arguments":"{\""}}`、`"location"`、`"\"}"` 逐片累加，openapi.yaml Assistants "Streaming with Functions" 示例）。

## 3. usage 字段（`CompletionUsage`）

来源：openapi.yaml `CompletionUsage` schema。文档页：https://platform.openai.com/docs/api-reference/chat/object

| 字段 | 类型 | 说明 |
|---|---|---|
| `prompt_tokens` | integer | 提示 token 数。**含缓存命中的 token**（见下） |
| `completion_tokens` | integer | 生成 token 数 |
| `total_tokens` | integer | prompt + completion |
| `prompt_tokens_details.cached_tokens` | integer | **缓存命中**的 prompt token 数。是 `prompt_tokens` 的**子集**，不是额外的 |
| `prompt_tokens_details.cache_write_tokens` | integer | 写入缓存的 prompt token 数（"The unadjusted number of prompt tokens written to cache"） |
| `prompt_tokens_details.audio_tokens` / `text_tokens` / `image_tokens` | integer | 输入侧各模态 token 拆分 |
| `completion_tokens_details.reasoning_tokens` | integer | **思考（reasoning）token 数** |
| `completion_tokens_details.audio_tokens` / `text_tokens` | integer | 输出侧拆分 |
| `completion_tokens_details.accepted_prediction_tokens` / `rejected_prediction_tokens` | integer | Predicted Outputs 相关 |

**流式 vs 非流式的 usage 返回时机（关键）**：

- **非流式**：响应体直接带 `usage`。
- **流式（默认）**：chunk 里**没有** usage（字段缺省）。
- **流式 + `stream_options: {"include_usage": true}`**：流**末尾、`data: [DONE]` 之前会额外多一个 chunk**，该 chunk 的 `usage` 字段是完整统计，且 `choices` 为**空数组**；其余所有 chunk 的 `usage` 字段为 `null`。官方注意事项："If the stream is interrupted, you may not receive the final usage chunk which contains the total token usage for the request."

**`cached_tokens` 含义与转换注意**：OpenAI 的 `prompt_tokens` 是**含**缓存命中的总数，`cached_tokens` 是其中的命中子集；而 Anthropic 的 `input_tokens` 是**不含**缓存的“新鲜” token，缓存读写是**另加的字段**（`cache_read_input_tokens` / `cache_creation_input_tokens`）。两者语义**方向相反**，转换层折算时不能简单等同（详见第 8 节差异对照）。

## 4. reasoning（思考/推理）：官方标准 vs DeepSeek 扩展

这是转换层最容易踩坑、也最需要讲清边界的一块。

### 4.1 官方标准（OpenAI）

在 `openapi.yaml` 全文搜索 `reasoning_content`，**零命中**——官方 Chat Completions 与 Responses 均无此字段。

官方表达推理/思考的三处：

1. **请求参数 `reasoning_effort`**（Chat Completions 请求体字段，`$ref: ReasoningEffort`）。枚举：`none` / `minimal` / `low` / `medium` / `high` / `xhigh` / `max`（默认 `medium`）。Chat Completions 与 Responses 请求都支持（对应文档：https://platform.openai.com/docs/guides/reasoning ）。注意：旧的 `ReasoningEffort` 枚举范围与第三方习惯（DeepSeek 等常用 `low/medium/high`）不完全一致，`none/minimal/xhigh/max` 是官方新增值。
   - 附带发现：Chat Completions 还有兄弟参数 `verbosity`（`low/medium/high`）控制简洁度；`max_completion_tokens` 描述明确「包含了可见输出 + reasoning token」。

2. **usage 里的 `completion_tokens_details.reasoning_tokens`**：推理消耗的 token 数（不含在普通文本里区分，但计入 completion_tokens 总数）。

3. **Responses API 才有「思考内容本身」**：
   - 响应 `output[]` 里可有 `type: "reasoning"` 的 item（openapi.yaml `ReasoningItem`），字段：`id`、`encrypted_content`（默认加密）、`summary[]`（`summary_text`）、`content[]`（`reasoning_text`）、`status`。
   - 流式事件：`response.reasoning_text.delta` / `response.reasoning_text.done`、`response.reasoning_summary_text.delta` / `.done`、`response.reasoning_summary_part.added` / `.done`。
   - 多轮时要把 reasoning item 的 `encrypted_content` 放回 `input`（尤其 `store:false` 或 Zero Data Retention）。

4. **Chat Completions 官方不流式吐思考内容**——没有 `response.reasoning_text.delta` 的 chat 等价物。官方 chat 流里推理只体现在 `reasoning_tokens` 的 usage 统计上，不暴露 thought 文本。

### 4.2 DeepSeek / 兼容方扩展（`reasoning_content`）

来源：https://api-docs.deepseek.com/api/create-chat-completion （官方一手）

| 位置 | 字段 | 说明 |
|---|---|---|
| 非流式响应 | `choices[0].message.reasoning_content` | "For thinking mode only. The reasoning contents of the assistant message, before the final answer." |
| 流式响应 | `choices[0].delta.reasoning_content` | 同上，逐 chunk 输出思考内容 |
| usage | `prompt_cache_hit_tokens` | 上下文缓存命中 token 数 |
| usage | `prompt_cache_miss_tokens` | 上下文缓存未命中 token 数 |
| usage | `completion_tokens_details.reasoning_tokens` | 推理 token 数（与 OpenAI 官方对齐） |

**结论**：
- `reasoning_content` 是 **DeepSeek 等兼容方的扩展字段，OpenAI 官方不存在**。转换层若上游是 DeepSeek 而客户端是 Claude Code，需要**显式**把 `delta.reasoning_content` 转成 Anthropic 的 `thinking_delta`；反向（官方 OpenAI 上游）则不会出现该字段。
- DeepSeek 的缓存语义是 `prompt_cache_hit_tokens` + `prompt_cache_miss_tokens` 二分的**独立字段**（`prompt_tokens` = hit + miss），与 OpenAI 官方的 `prompt_tokens`（含命中）+ `cached_tokens`（子集）两种表达**不同**，也不同于 Anthropic 的读写拆分。转换层按上游厂商区分处理。

## 5. Responses API 与 Chat Completions 的差异

来源：openapi.yaml（`Response`、`ResponseStreamEvent`、各 `Response*Event` schema）+ https://platform.openai.com/docs/api-reference/responses/create

### 5.1 请求结构差异

| 维度 | Chat Completions | Responses |
|---|---|---|
| 端点 | `POST /v1/chat/completions` | `POST /v1/responses` |
| 消息字段 | `messages[]` | `input`（string 或 `InputItem[]`） |
| 系统提示词 | `messages` 里的 `role: system` 消息 | 顶层 `instructions`（字符串或数组） |
| 输入条目类型 | `message`（role: system/user/assistant/tool） | `message` / `function_call` / `function_call_output` / `reasoning` …（`message` 内含 `input_text` 内容） |
| 工具结果 | `role:"tool"` + `tool_call_id` | `function_call_output` item，用 `call_id` 关联 `function_call` |
| 多模态 | content part `image_url` / `input_audio` / `file` | content part `input_text` / `input_image` / `input_file` / `input_audio` |
| 图片 | `{"type":"image_url","image_url":{"url":...}}` | `{"type":"input_image","image_url":... 或 "file_id":..., "detail":...}`（`InputImageContent`） |
| 推理 | `reasoning_effort` | `reasoning`（对象：`mode`/`effort`/`summary`/`context`） |
| 其它 | `n`、`logprobs` 等 | `previous_response_id`、`store`、`parallel_tool_calls`、`conversation` |

### 5.2 响应结构差异

- Chat Completion 响应：`object:"chat.completion"` + `choices[]`（`message` + `finish_reason`）。
- Responses 响应：`object:"response"` + `status`（`in_progress`/`completed`/`incomplete`/`failed`）+ `output[]`（有序 item 数组，item 类型 `message`/`function_call`/`reasoning`…）+ `usage`。
- Responses 的 `usage` 字段名也不同：`input_tokens` / `output_tokens` / `total_tokens` + `input_tokens_details{cached_tokens, cache_write_tokens}` + `output_tokens_details{reasoning_tokens}`（注意是 `input_tokens_details`，Chat 那边叫 `prompt_tokens_details`）。

### 5.3 流式事件（`ResponseStreamEvent` 联合类型）

Responses 流式**每个事件带 `sequence_number`**，事件类型（含但不限于，openapi.yaml `ResponseStreamEvent` 列出 50+ 个）：

| 事件 | 载荷关键字段 | 与 Chat chunk 的对应 |
|---|---|---|
| `response.created` | `response`（status=in_progress） | ≈ 首 chunk 的 id/model |
| `response.in_progress` | `response` | ≈ 首 chunk |
| `response.output_item.added` | `output_index`, `item` | 无直接对应 |
| `response.content_part.added` | `content_index` | 无直接对应 |
| `response.output_text.delta` | `item_id`, `output_index`, `content_index`, `delta`(string) | ≈ `delta.content` |
| `response.output_text.done` | 完整 `text` | 无对应（Chat 靠拼接） |
| `response.output_item.done` | `output_index`, `item` | ≈ 结束 chunk |
| `response.function_call_arguments.delta` | `item_id`, `output_index`, `delta` | ≈ `delta.tool_calls[].function.arguments` |
| `response.function_call_arguments.done` | `name`, `arguments`(完整) | 无对应（Chat 靠拼接） |
| `response.reasoning_text.delta` / `.done` | `item_id`, `output_index`, `content_index`, `delta`/`text` | Chat **无此字段**（官方） |
| `response.completed` | `response`（status=completed，含 usage、完整 output） | ≈ `data: [DONE]` 前的收尾（含 usage） |
| `response.failed` / `response.incomplete` | `response` | Chat 无对应（错误用 HTTP 状态/error chunk） |

**与 Chat Completions chunk 流的本质差异**：
1. Responses 事件是**结构化的、有显式 done 收尾**（`output_text.done`、`function_call_arguments.done`、`response.completed`），每个 item 有 `item_id`/`output_index`/`content_index` 三元定位，天然支持**多内容块、多输出项**；Chat chunk 只有平铺的 `choices[].delta` + `index`。
2. Responses 的 `function_call_arguments.done` 会给你**完整 arguments**，而 Chat 必须自己拼接分片。
3. Responses 流式以 `response.completed` 事件结束（不含 `data: [DONE]` 哨兵）；Chat Completions 流式用 `data: [DONE]` 结束（官方 `stream` 参数描述明确："stream terminated by a `data: [DONE]` message"）。
4. Responses 推理内容有专属的 `reasoning_text` 事件；Chat 没有。

**若转换层要支持 Responses 客户端或上游**，要点：Responses ↔ Chat 之间的消息/multimodal/工具结果是**一一可映射的距离最远的两套结构**（`output[]` order matters、`function_call`↔`assistant.tool_calls`、`function_call_output`↔`role:tool`）；usage 里 `input_tokens_details.cached_tokens` 与 Chat 的 `prompt_tokens_details.cached_tokens` 是同一缓存语义。

## 6. 多模态请求结构

### 6.1 Chat Completions 的 content 数组（content part）

来源：openapi.yaml `ChatCompletionRequestMessageContentPartImage/Audio/File/Text`。

| part `type` | 结构 | 说明 |
|---|---|---|
| `text` | `{"type":"text","text":"..."}` | 文本 |
| `image_url` | `{"type":"image_url","image_url":{"url":..., "detail":...}}` | `url` 是 "Either a URL of the image **or the base64 encoded image data**"；`detail` 枚举 `auto`/`low`/`high`（默认 `auto`）。**data URL 与普通 URL 是同一个 `url` 字段**，靠前缀区分 |
| `input_audio` | `{"type":"input_audio","input_audio":{"data":...,"format":...}}` | `data` 为 base64；`format` 枚举 `wav`/`mp3` |
| `file` | `{"type":"file","file":{"filename" / "file_data" / "file_id"}}` | 文件输入（`file_data` base64 或 `file_id`） |
| `refusal` | `{"type":"refusal","refusal":"..."}` | 模型拒答（assistant 消息里） |

**注意**：Chat Completions 里图片是 `image_url`；`input_image` / `input_text` / `input_file` 是 **Responses API** 的 content 类型（`InputImageContent` 的 `image_url` 是 "A fully qualified URL or base64 encoded image in a data URL"，另可用 `file_id`）。

## 7. 与 Anthropic 转换的差异对照表（核心踩坑点）

来源（OpenAI 侧）：openapi.yaml；来源（Anthropic 侧）：https://platform.claude.com/docs/en/api/messages-streaming （供应商区域限制可能重定向，停靠知识库确认的枚举）。

### 7.1 流结束与事件骨架

| 维度 | OpenAI Chat Completions | Anthropic Messages |
|---|---|---|
| 流结束标记 | SSE `data: [DONE]` 哨兵行 | `message_stop` 事件（类型化 JSON） |
| 首事件 | 无显式“开始”事件，靠首 chunk 的 `delta.role` | `message_start`（携带 id/model/usage/role） |
| 角色出现时机 | `delta.role` 只在**首个 chunk** | `message_start.message.role` |
| 增量事件 | 平铺 `choices[].delta` | `content_block_start` + `content_block_delta` + `content_block_stop`（每个内容块成对开/增量/关） |
| 结束属性 | `choices[].finish_reason`（最后一个 chunk） | `message_delta.stop_reason` + `message_stop` |

### 7.2 `finish_reason`（OpenAI）vs `stop_reason`（Anthropic）

| OpenAI `finish_reason` | Anthropic `stop_reason` | 备注 |
|---|---|---|
| `stop` | `end_turn` | 正常停止 / 命中 stop sequence 在 OpenAI 也是 `stop` |
| `stop`（命中 stop 序列） | `stop_sequence` | OpenAI 不区分，Anthropic 单独枚举 |
| `length` | `max_tokens` | 达到最大 token |
| `tool_calls` | `tool_use` | 模型调用工具 |
| `function_call`（已废弃） | — | OpenAI 旧枚举，新代码应只处理 `tool_calls` |
| `content_filter` | （无直接对应） | OpenAI 内容过滤；Anthropic 无等价枚举 |
| — | `pause_turn` | Anthropic 独有（用于 computer use 等暂停轮次），OpenAI 无 |
| — | `refusal` | Anthropic 独有（模型拒答）；OpenAI 用 `refusal` 内容字段而非 finish_reason |

**转换层注意**：OpenAI `finish_reason` 的枚举（`stop`/`length`/`tool_calls`/`content_filter`/`function_call`）与 Anthropic `stop_reason`（`end_turn`/`max_tokens`/`tool_use`/`stop_sequence`/`pause_turn`/`refusal`）**不是一一对应**，`stop_sequence`、`pause_turn`、`refusal` 三者在 OpenAI 侧无独立映射，反向转回时会信息丢失（`stop_sequence`→`stop`、`pause_turn`/`refusal`→`stop` 是丢语义的近似映射）。

### 7.3 工具调用分片拼接

| 维度 | OpenAI | Anthropic |
|---|---|---|
| 分片字段 | `delta.tool_calls[].function.arguments`（JSON 分片字符串） | `content_block_delta` 的 `input_json_delta.partial_json`（JSON 分片字符串） |
| 关联多个并行调用 | `tool_calls[].index` | `content_block_start.index`（`content_block_delta.index` 也带） |
| 完整参数何时出现 | **永不**——Chat 流必须自行跨 chunk 拼接 | **永不**——必须拼 `partial_json`；非流式才给完整 `input` |
| 调用名/ID 出现时机 | 首个 chunk 带 `id`/`function.name` | `content_block_start` 带 `id`/`name` |

**两者机制相同**：都是「index 关联 + 分片字符串拼接 + 首块带元数据」，转换是逐片搬运，但 OpenAI 侧 `index` 是**必填**、Anthropic 侧 `content_block_start`/`delta` 也带 index（含 0），搬运时注意 `index=0` 不能因 `omitempty` 被吞掉（Portunus 代码里已用 `*int` 处理）。

### 7.4 usage 语义（最容易算错）

| 维度 | OpenAI `CompletionUsage` | Anthropic `Usage` |
|---|---|---|
| 输入 token 计数 | `prompt_tokens` **含**缓存命中 | `input_tokens` **不含**缓存 |
| 缓存命中 | `prompt_tokens_details.cached_tokens`（子集） | `cache_read_input_tokens`（额外加） |
| 缓存写入 | `prompt_tokens_details.cache_write_tokens`（子集） | `cache_creation_input_tokens`（额外加） |
| 输出 token | `completion_tokens` | `output_tokens` |
| 推理 token | `completion_tokens_details.reasoning_tokens`（含在 completion_tokens 内） | 无独立字段（thinking 计入 output） |

换算关系（供转换层）：
- OpenAI → Anthropic：`input_tokens = prompt_tokens - cached_tokens`（若要把缓存拆成独立字段则 `cache_read_input_tokens = cached_tokens`、`cache_write_input_tokens = cache_write_tokens`）。
- Anthropic → OpenAI：`prompt_tokens = input_tokens + cache_read_input_tokens + cache_creation_input_tokens`，`cached_tokens = cache_read_input_tokens`。

### 7.5 思考内容的字段对应（第三方扩展必须显式处理）

| 来源字段 | 目标字段 | 官方/扩展 |
|---|---|---|
| DeepSeek `delta.reasoning_content` | Anthropic `thinking_delta.thinking` | **DeepSeek 扩展**，官方 OpenAI 无 |
| DeepSeek `message.reasoning_content`（非流式） | Anthropic `thinking` content block | DeepSeek 扩展 |
| OpenAI Responses `reasoning` item / `response.reasoning_text.delta` | Anthropic `thinking` | OpenAI 官方（仅 Responses API 有） |
| OpenAI `reasoning_effort` 参数 | Anthropic `thinking`（enabled+budget_tokens） | 官方参数，但**语义不同**：OpenAI 是离散档位（none/minimal/low/medium/high/xhigh/max），Anthropic 是显式 token 预算 |

## 8. 对 Portunus `backend/protocol/` 的落地提示

结合当前代码（`openai.go` / `stream.go` / `anthropic.go` / `responses.go`）审读，几个与官方规范需要对齐的点：

1. **`ChatCompletionChunk` 缺 `created` 与 `system_fingerprint` 字段**（`openai.go:124-130`）。官方 chunk 必带 `created`；`system_fingerprint` 虽废弃但 OpenAI 兼容上游（含部分代理）仍会返回。当前结构体解析时会静默丢弃，若 Gemini/Anthropic 目标需要这些元信息就会丢。至少补 `Created int64 \`json:"created"\``。

2. **`delta.content` 官方允许为 `null`，且 `refusal`、`function_call` 字段未建模**。当前 `ChunkDelta` 只建模了 role/content/reasoning_content/tool_calls，若上游拒答会丢 `refusal`。转换层若要完整，建议补 `Refusal` 字段并保留 `FunctionCall`（旧字段）的可选解析。

3. **`Usage.UnmarshalJSON`（`openai.go:104-121`）做了 `PromptTokens = prompt_tokens - cached_tokens` 的减法**，把 OpenAI 的“含缓存总数”转成了本项目自定义的“非缓存输入”语义。这是有意的规范化，但要意识到：**OpenAI 官方 `prompt_tokens` 本身是含缓存的**，若后续需要原样转回 OpenAI 上游（或对账官方计费），必须反向把 `CacheReadTokens` 加回去，否则对不上官方口径。

4. **流式 `usage` 只在 `include_usage: true` 的最后一个 chunk 出现，且 `choices` 为空**（openapi.yaml `CreateChatCompletionStreamResponse.usage` 描述）。当前 `openAIToAnthropicStream.Convert` 里 `if len(chunk.Choices) == 0 { ... return }` 前已先把 `chunk.Usage` 收进 `o.usage`（`anthropic.go:684-686`），这个顺序是对的；但要注意上游若不设 `include_usage`，则永远拿不到 usage，`Usage()` 需返回 nil 并回退估算（项目里 `Finish` 已做）。可以给上游转发时**主动注入 `stream_options.include_usage: true`** 以稳定拿到 usage。

5. **`responses` 转换集中在文本/function_call**，官方 Responses 还有 `reasoning` item（`responses.go:288` 明确注释“忽略 reasoning item”）和 `refusal`/`input_image`/`input_file` 等。若目标是完整支持 Responses 客户端/上游，reasoning 内容会丢失。至少应在 `OutputItem`/`ResponsesContent` 里保留 `reasoning` 类型与 `reasoning_text` 字段，避免上游返回思考内容时被丢弃。

6. **`finish_reason` 映射是一次性的、不可逆的**：`anthropicStopToOpenAI` 把 `stop_sequence`→`stop`，`openAIFinishToAnthropic` 把非 `stop`/`length`/`tool_calls` 的值兜底成 `end_turn`（`anthropic.go:531`）。这是合理的近似，但要意识到 `pause_turn`/`refusal`/`content_filter` 三者在双向映射里都**会丢失语义**，如需精确传递，建议在本项目 `Usage`/状态里保留原始 stop_reason，而不是只存映射后的 finish_reason。

7. **多模态 `image_url` 的 data URL 拆分**已在 `chatContentToAnthropicBlocks`（`anthropic.go:378-404`）里处理（`strings.HasPrefix(src, "data:")` → base64 + mediaType），与官方说法（`url` 字段既可普通 URL 也可 data URL）一致，无需改动；但要记得 OpenAI 侧还有 `input_audio`/`file` 两个 content part 类型未在此处处理（转换为 Anthropic 时会被静默忽略，Anthropic 无等价块，需显式丢弃或记录）。

## 9. 关键结论速查

- 流式 chunk 顶层 `id`/`created`/`model`/`object` **每个 chunk 都重复**；`delta.role` 仅首 chunk；`delta.content` 每 chunk 一段增量（可能 null）。
- `delta.tool_calls[].function.arguments` 是**分片 JSON、必须按 `index` 拼接**；非流式 `message.tool_calls[].function.arguments` 才是完整 JSON。
- `finish_reason` 枚举：`stop` / `length` / `tool_calls` / `content_filter` / `function_call`(废弃)，只出现在末 chunk（choices 空 + 含 usage 的 chunk 是 `include_usage=true` 的收尾）。
- usage：非流式必带；流式默认不带，`stream_options.include_usage=true` 才在 `[DONE]` 前额外多一个含 usage、`choices:[]` 的 chunk。`cached_tokens` 是 `prompt_tokens` 的**子集**（OpenAI 口径，与 Anthropic 相反）。
- `reasoning_content` **不是 OpenAI 官方字段**，是 DeepSeek 扩展（`choices[].message.reasoning_content` / `choices[].delta.reasoning_content`）。官方推理 = `reasoning_effort` 参数 + `completion_tokens_details.reasoning_tokens` + （仅 Responses）`reasoning` item。
- Responses vs Chat：`input`/`instructions` vs `messages`/system，`output[]` item vs `choices[]`，`input_tokens_details` vs `prompt_tokens_details`；流式事件类型化 + `sequence_number` + `.done` 收尾，Chat 是平铺 chunk + `[DONE]`。
- Chat `image_url.url` 同时承载「普通 URL」和「base64 data URL」；`input_image`/`input_text`/`input_file` 是 Responses 的 content 类型。
