# 已配置中转站与官方接口的思考强度探索对照

日期：2026-10-20。用户批准 12 次生成调用，禁止自动重试或补样；另各读取一次模型列表用于核对配置。测试提示为可验算的业务化合成场景，不包含用户真实业务数据，也未发送仓库文件或密钥给模型。

## 能证明与不能证明什么

请求发出前检查最终 reasoning_effort 确为目标值。请求被接受、返回思考内容，只能证明接口兼容。不同档位出现行为差异，可支持“此路由的档位设置影响输出”，不能从外部证明中转站逐字透传了指定字段。

直接证据需要中转站按请求 ID 提供脱敏的实际出站请求、目标模型/版本和关联到供应商的请求 ID。未经用户授权，本次不联系中转站人员。

两路使用已配置模型：乐聚-newapi / deepseek/deepseek-v4.1-flash，个人-deepseek 官方 / deepseek-flash。模型列表确认两别名存在，但无法确认它们指向完全相同的权重、版本、提示模板、采样设置或内部负载。不能用不同路由之间的单次耗时差判定是否丢参。

## 设计

2 个任务 × 2 条渠道 × low/high/max，共 12 次。每个条件仅一个样本，是探索测试，不是统计显著性实验。任务与档位配对顺序采用固定随机种子 20261020；每对两个渠道并发，单渠道不并发，减少时间段漂移但不能消除负载影响。

任务 1：生产数据交付管线的资源受限排程，8 个非抢占任务、3 个设备资源及共享操作员、前置依赖，求最短完工时间。使用 Claude Code 对应 Anthropic 输入形状（thinking adaptive + output_config.effort）经当前 Portunus 转换为 Chat。

任务 2：TTL/LRU 缓存代码排错，逐步模拟更新、到期边界、旧过期堆记录及容量淘汰，返回 15 次读取的实际/正确结果及缺陷集合。使用 Codex 对应 Responses 输入形状（reasoning.effort）经当前 Portunus 转换为 Chat。

共同控制：提示文本逐字相同（记录 SHA256）；无历史、无工具；stream=true；输出上限请求为 8192；没有主动设置 temperature/top_p，没有偷偷修改档位。Claude 入口最终使用 max_tokens=8192，Codex 入口最终使用 max_completion_tokens=8192；单任务内两条路由相同，但第三方是否认可该字段不可从请求成功推定。截断、超时、HTTP 错误都作为结果保留，不重试。

单次总超时 180 秒，响应头超时 60 秒。使用当前源码 ComposeUpstreamRequest/NewUpstream/NewHTTPClient，不经过常驻服务、分组 failover 或熔断，也不改持久配置/日志；这使每条已配置路由能被单独测量。没有启动 Claude Code/Codex CLI。

## 独立判分

排程先枚举 71 个合法拓扑优先序并按最早可行插入得到最优值 17，再逐答案检查完整性、资源重叠、依赖和最优性。另有下界证明：A 最早 4 分钟完成；所有 C/D/F 都依赖 A、占用同一 compute 资源共 10 分钟且均必须在 H 前完成；H 再用 3 分钟。因此 makespan≥4+10+3=17，有可行解达到此值。

缓存的 actual_reads 只执行事先固定的题目源码；correct_reads 由独立的直接过期清理与 OrderedDict 实现计算。绝不执行模型生成代码。判分同时检查两组读取及三个准确缺陷标识，答案不是只要合法 JSON 就算通过。

## 文件与复现

- cases.json：逐字提示及源协议。
- prepare_and_grade.py：准备题目、独立 oracle 和判分。
- oracle.json：标准值与一个可行最优排程，不发给上游。
- benchmark.go.txt：无凭据的运行器源码，需复制到临时 .go 文件后从仓库根运行并传本目录路径；运行时只读用户当前桌面应用 SQLite，凭据仅入内存。已有 results.jsonl 时拒绝覆盖，避免误重复计费。
- route_metadata.json：脱敏模型列表。
- pair_order.json：预先随机化的调用顺序。
- results.jsonl：每次原始观测和最终答案；不保存思考原文，仅保存长度、用量和最终答案。
- graded_results.json：独立判分结果。

## 已发现的执行约束

Codex 形状转换后的两条路由均有实际完成输出超过请求的 max_completion_tokens=8192（例如官方 max 的 completion_tokens=14098，reasoning_tokens=13997）。这说明不能把该字段视为本轮有效的统一总输出硬上限。DeepSeek 官方 Chat 文档列出的是 max_tokens，未列出 max_completion_tokens。这里仅报告观测及文档差异，不据此断言两站具体如何处理未知字段，也不在本次探索中修改业务转换器或追加调用。

因此按任务分别比较；不把缓存任务与排程任务合并计算一条“强度增长曲线”。若排程的 max_tokens 生效并发生 length 截断，必须在结果中标注，不能当成模型无法回答或低强度更聪明。

官方参考：https://api-docs.deepseek.com/api/create-chat-completion/ 。

## 完整结果

所有 12 次均 HTTP 200、finish_reason=stop、收到 [DONE]，通过独立判分；没有重试、超时或输出截断。两条路由返回的 response_model 均为 deepseek-flash，但名称一致不能证明实际权重版本一致。排程各次 prompt_tokens=360，缓存各次=770，输入相同。

表内为上游报告的 reasoning_tokens / 总耗时（秒）；不是网关估算。

| 任务 | 渠道 | low | high | max | 正确次数 |
|---|---|---:|---:|---:|---:|
| 资源排程 | 乐聚 | 5,220 / 26.82 | 6,262 / 31.71 | 6,096 / 30.60 | 3/3 |
| 资源排程 | DeepSeek 官方 | 7,602 / 38.46 | 2,263 / 11.56 | 5,591 / 27.23 | 3/3 |
| TTL/LRU 排错 | 乐聚 | 9,650 / 42.89 | 12,526 / 52.97 | 19,396 / 85.47 | 3/3 |
| TTL/LRU 排错 | DeepSeek 官方 | 11,456 / 47.61 | 14,146 / 59.76 | 13,997 / 62.70 | 3/3 |

上游报告用量合计：input_tokens=6,780，completion_tokens=115,081。仅统计本轮 12 次生成，不包含前一轮两次“1+1”调用。输出不等于最终答案长度，其中包含 reasoning_tokens。

## 结论及置信度

- **已验证，高置信度**：当前转换器在两类客户端输入上正确发出 low/high/max，两条配置路由都接受参数并完整完成任务。
- **已验证，高置信度**：本轮全部答案正确，因而这些任务和样本未区分不同强度的准确率收益。
- **行为支持，中等证据强度**：乐聚缓存排错的思考 token 为 9,650→12,526→19,396，max 约为 low 的 2.01 倍，耗时也增加；官方该任务 high/max 均高于 low。该现象与强度有影响相容，但每个条件只有一个样本，仍可能包含随机差异。
- **不能确认**：乐聚是否逐字转发 reasoning_effort、是否内部重映射、是否使用固定档位。排程任务的 max 不高于 high，官方 low 也高于 high，说明不能用单次 token 排序证明透传或丢参。
- **不能外推**：其他模型、saver 路由、复杂工程任务、长上下文、多工具调用、多轮推理的表现，本次均未测试。

## 最有区分力的后续证据

1. 直接证据：由中转站按 results.jsonl 的请求 X-Request-Id 和 response_id，提供实际出站 JSON（脱敏）、真实目标模型/版本、以及后端供应商请求 ID；仅展示接收到的入站日志不足以证明出站透传。若能由供应商日志独立对账则更强。本次没有联系中转站。
2. 行为实验：固定可确认的同一模型版本与有效 max_tokens 上限，增加有质量区分度的任务，对每个条件至少三轮随机重复；比较 token/耗时分布和准确率，不只比较一个值。三轮也只是起步，不能保证统计显著性。
3. 将输出上限兼容单独验证：本轮 Codex→Chat 的 max_completion_tokens 未形成所期望的 8192 总输出上限，严格实验应先统一有效预算。这是独立兼容问题，本轮未修改业务代码。

## 可复现性和清理

summary.json、graded_results.json 和 results.jsonl 均保留；不保存思考原文、密钥或真实业务数据。运行器保存在 benchmark.go.txt。临时可执行源码已删除，复现需将其复制为临时 .go 文件；生成调用须重新获得对应测试规模授权，不覆盖当前结果。
