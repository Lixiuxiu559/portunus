# Portunus 上游接入整体方案

日期：2026-10-21。状态：建议定稿，作为后续实施基线；本次只编写方案，未实施功能。

后续实施状态见[实施与验证记录](./2026-10-21-upstream-implementation.md)：A/B 与 C 功能已落地；真实账号验收和 D 专属适配仍按该记录标明边界。本方案正文保留原设计基线。

## 1. 目标与结论

吸收 New API 的厂商预设与适配机制，在 Portunus 已有协议转换、模型管理和分组路由之上，形成完整的上游接入流程：选择厂商 → 配置连接 → 获取或填写模型 → 保存 → 加入分组 → 主动验证调用。

采用四层结构：**厂商预设、渠道实例、连接适配、协议转换**。厂商和协议独立建模；现有 `Channel.Type` 继续表示协议。第一批实现配置预设和统一连接解析，后续根据真实需求增加特殊适配。

沿用本地聚合网关定位，不扩展多租户、余额、额度、计费、价格或成本路由。模型同步不能充当生成验证。现有分组仍负责对外模型名、成员选择和故障切换。

## 3. 总体结构与职责

```text
管理界面：选择预设，编辑连接，获取/选择模型，保存
                         ↓
厂商预设目录：可用协议、默认地址、字段提示、连接适配标识
                         ↓
渠道实例：厂商标识 + 协议 + 已保存地址/设置 + 凭据
                         ↓
统一连接解析与适配：校验、实际 URL、鉴权、模型发现
                         ↓
现有协议层：请求/响应转换、流转换、usage 与兼容处理
                         ↓
现有网关：发送、超时、重试、熔断、调用记录
```

具体约束：

1. 预设是创建时的模板。保存后以渠道实例中的值为准，升级预设不自动改写既有渠道。
2. 一个渠道实例绑定一种出站协议；同一厂商提供多种协议时，可创建多条渠道。客户端入口协议继续由现有转换层处理。
3. 厂商相同不代表模型、Key 权限或可用性相同。
4. 连接适配负责传输差异；协议层负责消息语义。厂商条件分支集中在连接模块，不散落到页面和网关。
5. 不根据模型名称或地址域名偷偷切换厂商、协议、鉴权或参数行为。
6. 不引入运行时插件加载、用户脚本或通用规则语言。先用结构化配置，特殊行为确有需求时再写 Go 适配器。

建议新增 `backend/upstream/`，包含预设目录、连接解析和厂商适配。依赖方向为 `api/model/gateway → upstream → protocol`，`upstream` 不依赖 `channel/model/gateway`，通过配置 DTO 接收连接信息，避免包循环。

现有 `protocol.NewUpstream` 保留为通用协议连接工厂；新模块包装它。第一阶段只统一上游连接入口，不搬迁成熟的协议转换实现。

## 4. 数据设计

### 4.1 厂商预设：后端内置目录

不新增厂商数据库表，目录随应用版本发布，前端通过 API 获取。

| 字段 | 语义 |
|---|---|
| `id` | 稳定字符串，例如 `generic`、`openai`；不使用数字数组下标 |
| `name` | 展示名称 |
| `profiles` | 支持的协议配置档，每档指定协议、默认 API 根地址、适配器、字段提示、模型发现方式 |
| `default_profile` | 创建时默认档位，不代表自动探测协议 |
| `model_suggestions` | 可选模型名称候选；未验证权限，不自动落库 |
| `help` | 地址与凭据的简明配置说明 |

目录的配置档是扩展单位，可以表达同厂商不同区域、不同产品端点。第一批仅发布已经核对的档位，不提前列出猜测可用的协议组合。

### 4.2 渠道实例

保留 `ID/Name/Type/BaseURL/Key/AutoSync/ThinkingCompat` 和现有模型关联。

新增字段建议：

| 字段 | 默认值 | 作用 |
|---|---|---|
| `provider_id` | `generic` | 厂商来源与展示标识 |
| `profile_id` | 空 | 使用过的配置档，便于编辑展示与诊断，不作为动态默认值来源 |
| `adapter_id` | `generic` | 固定的连接行为标识，由后端校验并与配置档匹配 |
| `connection_options` | `{}` | 版本化结构化连接设置，第一版只启用确有需求的字段 |

`connection_options` 第一版支持 `schema_version` 和模型发现模式 `model_discovery = api/manual`；若实施批次确需额外 Header，再开放显式 Header 配置。后续 Azure 的 API 版本、AWS 区域等按适配器提供独立 schema。

地址、协议、thinking 设置和所需连接选项在创建时展开保存；服务端对直接 API 创建也执行相同默认展开。区分字段缺失与显式值，`false/0` 不被默认值覆盖。既有渠道不重新套用厂商默认值。

认证秘密继续通过专门写入字段处理，响应只返回是否已设置或脱敏信息；不能通过 `connection_options` 原样回传秘密。需要新增凭据种类时再扩展结构化凭据，第一批不改写现有 Key 存储方案。

### 4.3 模型与分组

- 继续使用独立模型表，不把模型列表存成渠道上的逗号字符串。
- 模型表保存上游真实名称，分组名是客户端模型名。
- 不新增第二套模型映射；Azure 部署名等若后续需要，作为该适配器的明确模型配置单独设计。
- 首期同步保持只新增。下架检测、自动删除和停用状态不是本方案的前置条件。

## 5. 统一连接解析

引入 `ConnectionConfig → Resolve → Connection`，预览模型、同步、真实验证、网关转发全部经过同一入口。

解析结果包含固定协议、适配器、实际 API 根地址、对话与模型端点、鉴权构建方式、模型发现能力。解析过程不发送网络请求。

### 地址规则

1. Portunus 统一把 Base URL 定义为 **API 根地址，包含该服务要求的版本或路径前缀**。协议接入器只追加操作路径。例如本地测试地址 `http://localhost:1234/v1` 对 Chat 追加 `/chat/completions`。
2. 厂商预设直接给出完整 API 根地址。具体值在实施时核对官方文档，不把 New API 的“域名根地址”照搬过来。
3. 去掉首尾空白与末尾多余 `/`，保留自定义路径前缀；不自动删除或补上任意 `/v1`。
4. 普通根地址输入禁止混入凭据、query、fragment。确需 query 参数的服务由适配器显式构建；检查生成端点避免重复拼路径。
5. 对完整操作 URL 给出明确纠错提示；首期不提供任意 URL 模板模式。
6. 保留本地 HTTP 服务接入，网络策略沿用现有本机管理边界。

旧渠道地址不自动改写。迁移后依旧按已有根地址直接追加原有操作路径，保证原来可工作的配置得到相同 URL；新的严格地址校验用于新建和连接字段发生变化时。

### 鉴权与覆盖顺序

适配器生成协议所需的鉴权和版本头。若开放自定义 Header，则顺序为协议默认 → 允许的普通自定义头 → 受保护的凭据和传输头校验。

鉴权由 Key/专用凭据字段管理；`Host`、`Content-Length` 等传输头不可随意覆盖。Header 按大小写不敏感处理。需要特殊鉴权的厂商由适配器实现，不让普通 Header 偷换认证方式。诊断输出不得含 Key、认证头或带凭据 URL。

第一阶段不新增任意 JSON 参数覆盖。现有 thinking、预算和模型名改写仍走原有协议装配逻辑；未来确需厂商请求修正时，在连接模块中提供有测试的具名行为，不覆盖用户显式参数而不留记录。

## 6. 管理流程与界面

### 6.1 新建渠道

1. 选择厂商，默认提供“通用兼容服务”。
2. 选择协议配置档，自动填入 API 根地址及适用默认设置。
3. 填写渠道名和 Key，可修改地址；界面展示当前目标协议和最终操作端点预览。
4. 点击“获取模型”，仅发现模型，不创建渠道、不执行生成。
5. 勾选要保存的模型，也可手动补充。获取失败时允许使用手动模型继续保存。
6. 保存渠道及已选择模型；成功后提示到分组页添加这些模型。

切换厂商/配置档会使已获取模型列表与测试结果失效。仅自动替换尚未被用户修改的默认字段；对已有自定义地址提供显式“应用预设”操作，避免覆盖输入。创建默认开启与否按照发现能力确定：API 发现模式允许自动同步，手动模式默认关闭自动同步。

### 6.2 模型保存闭环

新建请求增加可选 `models`：

- 字段缺失：兼容旧调用方，只创建渠道；旧调用方自行同步的行为继续可用。
- `[]`：明确不创建任何模型。
- 非空数组：去空白、去重、校验后，与渠道在同一数据库事务中保存。

新前端提交明确选择结果，保存后不再无条件全量同步。未选择模型时可保存空渠道，但要提示尚未加入分组可用。模型获取在事务外执行，数据库事务内不等待上游。

手动“一键同步”与自动同步均明确表示“新增发现的全部模型”。它们不是选择预览的保存操作，也不承诺维持用户曾经选择的子集。界面开启自动同步时直接说明会加入以后发现的新模型。

### 6.3 编辑渠道

- 加载已保存值，不因预设升级重新填充。
- Key 留空代表不修改，预览和测试可在后端复用该渠道已保存的 Key；不把脱敏文本当成新 Key。
- “获取模型”使用当前表单配置，仅生成待导入列表；未保存的连接不会影响正式调用。
- “保存并导入所选模型”事务性更新连接和新增模型；本轮不把未勾选的既有模型解释为删除。
- 删除既有模型继续使用独立操作，并复用现有引用处理；预览列表中的取消勾选只影响待导入项。
- 已保存配置的同步入口保留在渠道列表；连接字段变化使旧测试结果失效。

修改协议仍影响该渠道下全部模型。保存前展示影响的模型和分组范围；不静默重建模型 ID、不修改分组引用。

### 6.4 测试与能力展示

分开表达三件事：

| 状态 | 能证明什么 |
|---|---|
| 配置有效 | 本地校验通过，能够解析目标端点 |
| 已获取模型 | 模型列表接口成功，不代表允许生成 |
| 调用验证通过 | 某次指定模型、指定模式的真实请求成功 |

真实验证必须由用户主动点击；显示模型、流式/非流式模式、输出 token 上限，并提示会消耗上游额度。使用固定的小请求和有上限的输出预算，不自动轮测所有模型。输出上限不等于总消耗保证，也不展示估算费用。

渠道测试仅验证单个连接，禁止故障转移掩盖失败。分组级验证另外复用实际路由与重试。验证成功不把厂商所有模型或协议标成已支持。

首期不做能力探测系统；只显示已经实现的协议配置档、模型发现模式和本次验证结果。

## 7. API 契约

以下路径相对于现有管理 API 的 `/api` 前缀，沿用本机管理鉴权边界。

| 接口 | 行为 |
|---|---|
| `GET /upstream-presets` | 返回预设、协议档、默认配置与表单字段说明，不返回秘密 |
| `POST /channels/resolve` | 纯本地解析草稿配置，返回安全的端点和校验结果 |
| `POST /channels/preview-models` | 扩展原接口，使用草稿配置获取模型，不落库 |
| `POST /channels` | 扩展原创建接口，支持厂商字段和所选模型事务保存 |
| `PUT /channels/:id` | 扩展原更新接口，支持连接修改与所选新增模型事务保存 |
| `POST /channels/:id/sync` | 保持按已保存配置执行新增同步 |
| `POST /channels/test` | 对草稿或已保存连接做用户触发的单模型真实验证 |

草稿预览、解析、测试允许带 `channel_id`，服务端加载原配置后叠加显式提交字段，复用未提交的秘密。必须校验该渠道存在，不能通过这个入口读取原 Key。旧版预览接口的 `type/base_url/key` 请求继续有效。

超时、取消、上游非成功状态和协议解析失败返回可识别错误阶段，不只返回一个“失败”。模型获取和测试接受请求 context，页面取消或连接断开时取消上游请求。

## 8. 运行时链路与观测

正式调用继续：分组选择模型 → 统一解析渠道连接 → 原有协议装配 → 连接适配构建 URL/鉴权 → 原有网关发送与流处理 → 原有日志及熔断。

特殊适配器不拥有新的 HTTP 请求循环，不绕过网关超时、取消、重试、流式收尾或 token 预算重试。特殊认证若需完整请求信息，可扩展连接构建接口；仍由网关统一发送。

尽量复用现有错误分类与上游尝试记录。增加诊断上下文：厂商标识、适配器、协议、安全处理后的目标端点、失败阶段；保持历史记录可读。调用测试增加明确来源，不能污染正常客户端成功率或触发分组故障切换。

模型发现错误只影响该次管理操作，不标记整个渠道不可调用；也不直接计入正式调用的熔断器。

## 9. 厂商接入范围

### 第一批：现有四协议可以承接的预设

候选：通用兼容服务、OpenAI、Anthropic、Gemini、DeepSeek、OpenRouter、硅基流动、火山方舟、阿里云百炼、Moonshot。

每个候选上线前逐档核对官方地址、协议、Key 形式、模型发现和实际请求。只发布通过验证的档位；不因为 New API 存在该厂商，就直接宣称 Portunus 全能力支持。候选厂商可按实施结果分批上线，不让首批数量阻塞核心能力交付。

第一批只承诺现有对话协议范围，不由厂商名称引申图片、音频、视频、Embedding、Rerank 等接口支持。

### 后续：需要特殊连接行为的厂商

Azure、AWS Bedrock、Vertex AI，以及使用 OAuth、临时令牌、签名或专用账户流程的上游，按实际使用需求单独设计和接入。每个适配器必须覆盖鉴权、模型发现或手动模型方式、流式请求、错误语义和取消。

余额查询、多 Key 池、自动禁用、远程预设市场、脚本适配器不进入本轮范围。

## 10. 迁移与兼容

1. SQLite 仅添加新列，旧记录按 `generic` 厂商、`generic` 适配器和当前协议解释。
2. 不按域名回填厂商，不重写地址，不重新获取或覆盖 Key，不重建模型或分组。
3. 空/缺省连接设置保留旧行为；未知厂商展示为通用或原标识，不丢失数据。未知非通用适配器必须报明确错误，不能悄悄改用通用鉴权。
4. 新建严格校验与旧配置读取分开；只改渠道名称等无关字段时，不强迫修正历史连接。
5. 默认配置仅在创建或显式应用预设时复制。后续升级可以提示默认配置变化，但由用户应用。
6. 升级前备份数据库；新增特殊适配器后的降级以备份恢复为保证。不承诺旧程序可以正确调用它不认识的新适配器。

## 11. 实施批次与验收

| 批次 | 内容 | 完成标准 |
|---|---|---|
| A：基础与兼容 | 内置预设目录、新增字段、统一连接解析、迁移、模型发现/正式请求统一入口 | 旧渠道生成相同端点和鉴权；四种协议现有测试通过；新预设默认值能被稳定解析 |
| B：接入闭环 | 创建/编辑共用表单能力、预览、手动添加、所选模型事务保存、同步语义 | 用户选中的模型才被本次保存导入；失败不遗留半条渠道；编辑预览使用草稿且不改正式配置 |
| C：验证与首批交付 | 用户主动测试、诊断结果、首批厂商逐档验证、说明文档 | 可区分列表成功与调用成功；测试不自动切换渠道；至少每个发布档具备对应验证证据 |
| D：按需扩展 | Azure/AWS/Vertex 等专属适配与结构化字段 | 每个适配器独立通过连接、非流式、流式、错误、取消验收后再进入支持列表 |

A、B、C 共同构成首个完整版本；D 不是这个版本的前置条件。实施阶段同步更新产品定义和接入说明，不能把本方案的目标提前写为已交付状态。

### 关键测试与验证

- 地址：版本前缀、自定义路径、末尾斜杠、错误完整操作 URL、旧渠道端点兼容。
- 鉴权：四协议原有鉴权一致，普通 Header 不覆盖受保护字段，诊断响应不泄露秘密。
- 默认值：未提交字段、显式空值和显式 false 的语义；修改预设目录不改变已保存渠道。
- 模型保存：去重、空选择、缺失字段、事务回滚、手动模型、同步重复执行、分组引用保持。
- 编辑：复用旧 Key、替换 Key、草稿预览、取消编辑、修改连接后测试结果失效。
- 网络：列表超时、401/403、404、非 JSON、测试取消、流式错误及超时。
- 网关：原有协议转换、reasoning、工具调用、Responses 生命周期与预算重试不回归。
- UI：创建与编辑共享预设来源，字段不会被切换操作静默覆盖，用户能完成渠道到分组的完整流程。

先运行受影响 Go 包和前端构建/已有检查，再运行网关关键回归。真实调用单独记录厂商档位、测试时间、模型、模式和结果；未经实际验证的能力明确标注。

## 12. 最终决策摘要

采用“稳定的协议核心 + 可扩展的连接适配 + 数据化厂商预设”。保留现有模型与分组体系，先交付少量验证过的厂商和完整配置闭环。新增厂商时，先判断能否增加预设解决，再判断是否需要连接适配，只有出现新的消息语义时才扩展协议层。
