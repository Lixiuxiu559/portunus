# 模型/渠道删除：引用影响预览与级联清理测试设计

## 1. 范围与依据

范围：`backend/api`（模型、渠道删除及影响预览）、`backend/group`（引用查询与清理）、`backend/model`（删除语义）、前端渠道/模型删除确认弹窗与 API 封装。基线：`9bf6dbb` 工作区。

已确认的用户决策（2026-10-27 对话）：采用“影响预览＋明确确认＋事务级联清理”；允许删除被引用资源；不自动补位；保留分组与历史调用记录；清理由后端保证，直接调 API 也一致。

| 规则编号 | 业务规则 | 来源 | 未确认事项 |
| --- | --- | --- | --- |
| R1 | 删除前可预览受影响分组、将移除的成员、手动激活项清除与空组风险；渠道另含模型数量与余额来源提示 | 用户确认的整改建议 | 预览为只读，具体接口形状由实施定 |
| R2 | 预览/查询本身不修改任何业务数据 | 同上（只读预览） | 无 |
| R3 | 单模型确认删除后：模型删除、引用它的分组成员删除、指向这些成员的 ActiveItemID 清零；其他模型/成员不受影响 | 当前缺陷修复＋用户决策 | 无 |
| R4 | 渠道确认删除后：余额来源、渠道模型、相关分组成员、渠道在同一事务清理，ActiveItemID 清零；保留既有渠道级联行为 | 现有 `deleteChannel`＋用户决策 | 无 |
| R5 | 不自动选择替代成员：手动 ActiveItemID 只清零；failover 剩余成员及 priority/ID 顺序不变 | 用户决策 | 无 |
| R6 | 分组与历史调用日志保留；最后一个成员移除后分组仍存在（空分组按现有规则不进 `/v1/models`） | 用户决策＋`gateway.listModels` | 无 |
| R7 | 删除事务任一步失败时整体回滚，不留半清理状态 | 用户决策（事务级联） | 无 |
| R8 | 无引用、空组、目标不存在等边界行为明确：无引用可正常删除；不存在目标按现有错误分类返回；重复删除不伪造成功影响 | 现有 `classifyError`＋边界推导 | 无 |
| R9 | 前端确认前展示真实影响数据与危险提示，加载失败给重试且不允许误删；确认中防重复提交；取消不发删除请求 | 用户决策（明确确认）＋现有弹窗模式 | 现有无组件 DOM 测试设施，见 §3 |
| R10 | 直接调用删除 API（绕过前端）也得到与 R3/R4 相同的清理结果 | 用户决策 | 无 |

## 2. 测试设施

- 后端：Go `testing`＋`httptest`＋Gin 测试路由＋临时 SQLite（`t.TempDir`）。复用 `backend/api/channel_test.go` 的 `setupCascadeTest`、现有 `TestDeleteChannelCascades`、`group_creation_test.go` 的触发器回滚手法。
- 前端：`node --test "src/**/*.test.js"`，纯函数/状态逻辑测试（如 `groupModelSelection.test.js`、`newAPIDetection.test.js` 的工厂＋可控 Promise 模式）。**无 DOM/组件渲染测试设施**，不新增框架；弹窗可测逻辑抽到纯模块后覆盖，DOM 交互列为手工/后续缺口。
- 路由回归：`backend/router/router_test.go` 验证删除后 failover 可解析剩余候选。

| T9 / R5 | failover 组含 m1(p0)、m2(p1)、m3(p2)，删除 m1 后 `router.Resolve` | 返回 m2、m3 且顺序不变；无自动重排/补位 | `backend/router`＋删除后 `group.GetByName` |

## 5. 交给实施工作流

优先级：P0＝T3/T4/T5/T6/T9（数据一致性与路由可用性）；P1＝T1/T2/T7/T8/T10＋F1–F6（预览与交互）。
建议命令（由实施阶段执行）：`go test ./backend/api/ ./backend/router/ ./backend/group/ ./backend/model/ -run 'Delete|Cascade|Resolve' -v`；`cd web && pnpm test`；随后全量 `go test ./...`、`go vet ./...`、`pnpm run typecheck`。
禁止：为通过测试改为禁止删除被引用资源、自动选择替代激活项、删除分组或历史日志。
