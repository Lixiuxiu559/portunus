## 1. 产品定位

**Portunus 是本地运行的多上游 API 聚合网关，将不同渠道的模型组织为模型分组，统一向客户端和应用提供服务。**

核心价值：上游集中接入，模型按用途分组，调用方使用稳定入口；切换上游和调整路由时，无需反复修改调用方配置。

“本地 New API 聚合＋模型分组服务”用于内部理解方向。对外文案直接描述本地聚合和分组路由，具体能力以本文为准。桌面应用是交付形态，Claude Code、Codex 及其他应用是调用方。

“对外服务”首先指向调用方提供 API，包含本机应用和符合访问边界的局域网设备；公网发布不是当前默认承诺。

## 2. 用户与主要任务

| 用户 | 主要任务 | 成功结果 |
|---|---|---|
| 管理多条官方或中转 API 的个人开发者 | 集中管理地址、密钥和模型 | 客户端只维护一个网关入口 |
| 同时使用多个 AI 工具的用户 | 将 coding、daily 等用途映射为分组 | 不同客户端复用同一分组，按需调整上游 |
| 开发本地应用或自动化脚本的用户 | 通过标准接口调用分组 | 应用逻辑不依赖某条渠道的模型 ID |
| 需要其他设备调用的本地服务所有者 | 在明确访问边界下开放分组 | 调用方只能使用获准的服务，不能管理网关 |

首阶段仍采用单所有者管理模式。账户、充值、多租户结算、团队权限、每调用方额度与公网托管不列入此次页面调整范围。

## 3. 核心对象与术语

| 对象 | 定义 | 示例 / 规则 |
|---|---|---|
| 上游渠道 | 一组上游地址、凭据和接口协议 | 官方 API、New API 实例、第三方中转站均以相同方式接入 |
| 上游模型 | 某个渠道下可调用的模型条目 | 相同模型名在不同渠道是不同资源 |
| 模型分组 | 用户组合的一组上游模型，以及请求路由策略 | `coding`；**分组名称就是客户端请求中的 model** |
| 分组成员 | 分组引用的某个渠道模型 | 乐聚的某模型、官方的某模型；显示渠道来源 |
| 服务接入 | 网关地址、访问令牌、接口说明和分组调用示例 | 调用方不应使用上游密钥访问 Portunus |
| 调用记录 | 一次客户端请求及其上游尝试的观测信息 | 分组、实际命中渠道/模型、用量、缓存 token、耗时、错误 |

保留“模型分组”这一产品对象，不再增加一层需要用户重复维护的“虚拟模型”或“服务”。一个分组直接构成一个对外模型服务。首阶段沿用单一分组名，先明确其稳定标识含义和改名影响。

### 必须如实描述的规则

1. `/v1/models` 只返回非空分组，不直接公开渠道模型。非空仅表示已配置成员，不能等同于当前可调用或全部成员能力相同。
2. 模型同步目前只补充新发现的模型，保留已有模型，不自动删除上游消失的模型；同步不执行生成验证。
3. 界面“记录数”仍按旧 logs 表的 relay 日志行计数，普通重试和目标切换可产生多条同 request_id 记录。独立 upstream_attempts 表已为每次显式 http.Client.Do 留痕，包括预算字段兼容重试，但不混入旧统计。应用尝试数不等于上游收到请求数或 Transport 物理发送数；历史与写库失败可能缺失记录，不能推断完整链路。
4. 产品不提供模型价格配置、默认价格套用、调用费用计算或费用统计。保留上游报告的 token 和缓存 usage；缺少 usage 不能被解释为没有消耗。实际收费以供应商账单为准，手动执行真实调用仍可能产生费用。
5. 上游支持思考强度、上下文、工具等能力与否，不由模型名称推断；同协议透传、跨协议映射，不让用户在分组再配置一遍客户端参数。
6. 此前真实预算验证发现的 Responses 固定 completed 问题已修复：跨协议流式、非流式转换将 `length` 映射为 `incomplete`，原因 `max_output_tokens`；流式发送 `response.incomplete`。内容过滤对应原因 `content_filter`，反向转换保留上述原因；正常完成与工具调用继续返回 completed。截断时保留部分输出和总用量，收尾时尚未完成的工具项标记 incomplete。同协议直通保留原事件，并提取截断事件中的 usage。已完成本地回归及两条上游、实际 Codex CLI 的[修复后实机验证](../research/2026-10-20-responses-lifecycle-fix/README.md)：预算截断原因已被客户端识别，正文 message / reasoning 生命周期与终态 output 已补齐，两条上游的 CLI 均实际显示 OK，真实缓存命中明细与上游、日志和 CLI 一致；不能用 HTTP 200 或 CLI 退出码 0 代替语义与正文检查。后续两条上游与本机 Codex App Server 的[只读动态函数工具及同会话双轮验证](../research/2026-10-20-responses-tools-multiturn/README.md)也已通过；内容过滤真实触发、内置 shell / 命名空间工具、工具与思考同时开启及图形客户端尚未验证。

## 5. 页面信息架构与目标方案

P0 采用六个主导航，调整职责与顺序，不新增仪表盘：

**模型分组 → 上游渠道 → 上游模型 → 服务接入 → 调用记录 → 设置**

默认进入模型分组。首次使用时通过分组空态引导“添加渠道 → 获取模型 → 创建分组 → 接入”；实际调用验证目前由用户手动执行接入示例，应用内验证按钮属于 P1。服务运行状态可放在公共顶栏和服务接入页，已有统计放在调用记录页。

### 5.1 模型分组：产品主入口

当前：分组卡片支持增删改、添加成员、切换手动项、故障转移排序、接入与调用记录跳转；创建默认手动策略，允许跨页、跨渠道一次选择多个成员，并配置当前手动成员或故障转移顺序。已完成 [1102 条模型的隔离实机浏览器验证](../research/2026-10-20-group-model-selection/README.md)。

建议：

- 标题与说明明确“把多个上游模型组合为稳定的调用入口”；名称字段写明“客户端 model”，示例使用 `coding`、`daily`。
- 卡片优先显示分组名、策略、成员/渠道数，以及配置是否完整；成员行保持“模型＋渠道”可辨认。
- 增加“接入此分组”“查看调用”“验证调用”动作；接入页和日志页自动携带当前分组，不让用户重复选择。
- 创建时允许一次选择多个成员，随后按策略配置：手动选当前成员；故障转移设主备顺序；轮询说明失败顺延行为。保留默认手动策略，避免未经用户选择就自动切换供应商。
- 只在需要顺序的策略下强调拖拽优先级，避免让手动或轮询用户误以为顺序同样决定主备。
- 改名、删除或移除关键成员前显示对调用入口和当前策略的影响；不能改完名称后暗示客户端还能使用旧名字。
- 无成员、手动未选择有效成员属于“配置不完整”；全部熔断属于运行态。没有调用证据时显示“未验证”，不显示“在线”。

验收：用户能从一个分组完成“配置成员 → 理解路由 → 获取接入参数 → 发起验证 → 查到记录”的闭环；更换成员不会改变分组 model。

### 5.2 上游渠道：连接与模型发现

当前：卡片展示协议和地址，支持编辑、删除、同步；创建支持预览，保存后再同步。

建议：

- 名称、上游协议、地址、凭据仍是核心字段；协议与供应商身份分开解释，官方和各类中转站共用相同流程，不新增按品牌必填的能力表。
- 列表增加模型数量、最近同步时间/结果、最近调用结果；分别标明证据来源，避免一个绿色点混淆同步与推理可用性。
- “查看模型”带渠道筛选，“创建分组”带入本渠道模型，删除前展示受影响的分组。
- 显式区分“获取模型列表”和“验证实际调用”。后者显示测试模型和输出预算，由用户主动触发，不在页面打开或同步时自动产生生成费用。
- 校准预览交互：当前预览中移除模型不会随创建请求提交，保存仍会同步全部模型。建议首阶段将预览改为只读，若以后支持选择性导入，必须让保存行为真正尊重选择。

### 5.3 上游模型：资源目录

当前范围：模型目录按渠道/名称筛选、手动新增，供分组引用。本轮移除价格和货币字段、默认价格套用与价格编辑。

建议：

- 标题改为“上游模型”，说明“这是分组可使用的资源，不是直接交给客户端的 model”。
- 主要信息为模型 ID、所属渠道、分组引用和加入分组入口，不配置模型价格。
- 手动新增继续保留，覆盖上游无法列出模型但已有可调用 ID 的场景。
- 选成员已改为按渠道、名称服务端搜索，每页 20 条；跨页保留选择，分组成员名称与渠道直接来自分组响应，不再受前 1000 条目录限制。
- 模型删除、渠道删除、同步发现模型消失时，应说明引用影响；同步发现消失项不能直接自动删除仍被分组引用的配置。

### 5.4 服务接入：统一对外入口

当前：服务接入页集中网关地址、分组、Portunus 令牌、监听范围、通用 API 示例与客户端指南；设置页提供跳转，不再重复编辑令牌与监听范围。

页面按以下职责组织；其中应用内实际调用验证入口仍待补齐：

1. **服务信息**：运行状态、本机地址、访问范围；切换 LAN 后显示可用设备地址，不能让其他设备复制 127.0.0.1 或 0.0.0.0 作为目标地址。
2. **访问令牌**：查看、复制、生成/重置及影响说明。沿用现有单令牌，不在本轮增加多调用方权限体系。
3. **分组选择与连接参数**：model、对应 Base URL、认证方式、模型列表入口。

## 7. 产品验收标准

1. 新用户能清楚区分上游密钥与 Portunus 令牌、上游模型 ID 与分组 model。
2. 创建 coding 分组后，可从该分组直接获得三个客户端协议的接入示例；实际更换成员不要求改客户端。
3. 三种策略的界面说明与后端行为一致；流中断不被描述为可无损重放。
4. 空组、手动项失效、未验证、最近成功、熔断各自有准确含义。是否改变 `/v1/models` 对配置不完整分组的公布规则，在实施前确定，避免静默改变已有 API 行为。
5. 同协议保留参数，跨协议按字段语义转换，不根据模型名猜能力；用户无需重复配置思考强度或预算。
6. 从日志能看出请求了哪个分组、实际使用哪个渠道模型；请求和尝试统计不混淆；保留 token 与缓存用量，不提供价格配置或费用统计，缺少 usage 不宣称没有消耗。
7. 开启对其他设备服务后，远端调用方不能读取管理接口、上游凭据或管理服务令牌。
8. 文档区分当前能力、规划和限制；一次连通验证不被扩展成所有任务/所有成员都支持的承诺。
