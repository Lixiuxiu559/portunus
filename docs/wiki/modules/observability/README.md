## 用途与边界

观测模块用于回答请求选了哪个分组、命中哪个渠道模型、返回什么用量和错误，以及已采集到哪些尝试和切换事件。它不提供完整提示词/响应正文存储，也不把持久化记录包装成准确的客户端请求终态。

`Log` 保留原有 relay 日志和 token/缓存聚合；历史价格、货币和费用列保留旧值但不进入活跃管理接口或统计。`UpstreamAttempt` 与 `RoutingTrace` 独立存储，不重复累加 token，也不混入旧日志行计数。

## 主要流程

### 查询与关联

管理路由统一位于 `/api/logs`：列表、统计、按请求归并、尝试、切换诊断及按截止时间删除。筛选支持 API Key、渠道、分组、模型、精确请求 ID、客户端协议、结果与时间范围等。

- 日志视图按筛选后的日志行分页，统计卡使用同一筛选。
- 归并视图先以筛选选中关联项，再从该请求 ID 的**全部持久化日志**生成摘要。后端数据库完成分组和分页，不是前端只合并当前页。
- `latest_log` 按最大写入 ID 选取；最近时间、渠道、模型和结果来自同一行。`first_at`/`last_at` 是时间边界，不能假定与写入顺序相同。
- 无 ID 历史日志使用独立 `log:` key，真实请求使用 `request:` key，避免碰撞。

### 尝试与诊断

`UpstreamAttempt` 按 `request_id` 和 `sequence` 关联，记录首次、普通重试、切换和预算兼容等原因。管理查询必须提供精确请求 ID，按 sequence、ID 升序分页。装配失败、冷却或并发拒绝未到达 `Do` 时，不生成 HTTP 尝试。

`RoutingTrace` 另存候选跳过、准入、租约、备用选择与停止原因；事件有界，截断数量和最终摘要分开保留。查询必须提供精确请求 ID，缺失时不从其他日志反推。

### 正确解读结果

| 看到的证据 | 不能推出的结论 |
|---|---|
| 最近持久化日志成功 | 客户端已完整收到最终响应或请求最终成功。 |
| 尝试序号为 1、2、3 | 采集完整、没有尾部丢失或上游只收到三次。 |
| 尝试列表为空 | 实际 HTTP 调用为零；也可能未采集、已清理或写入失败。 |
| 切换诊断的交付标记 | 客户端完整接收；它只表示开始尝试写模型响应。 |

保留 token 和缓存 usage，缺少 usage 不等于没有消耗。过期清理按日志记录时间、尝试/诊断开始时间执行，因此旧请求的关联证据可能逐渐减少。
